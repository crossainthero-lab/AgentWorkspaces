# Security model

**AgentWorkspaces gives graphical isolation and an authenticated, scoped control API. It is not a security boundary against a hostile program running as you.** The optional `--sandbox` adds filesystem and process confinement for the apps of one workspace; what it does and does not cover is listed below. Everything stated as implemented is covered by a test named in this document; anything else is listed under "not provided" or "not tested".

## What is protected, from what

| Threat | Protection | Evidence |
|---|---|---|
| Another user on the machine talks to the API | socket `0600` in a `0700` directory; the daemon also refuses any peer whose kernel-reported uid (`SO_PEERCRED`) is not its own and logs `auth.refused_uid` | unit test with an injected foreign uid; real socket modes checked in `UnauthorisedAndWrongIds.test_other_user_peer_check_exists_on_the_real_socket`. A real connection from another uid was **not** tested (needs a second account) |
| An agent drives another agent's workspace | every request is authorised credential -> workspace -> scope before anything runs; a workspace credential is bound to one workspace id | unit `Authorisation.*`; real `ConcurrentAgents`, `UnauthorisedAndWrongIds` |
| A wrong, missing or stale workspace id | agents get `E_FORBIDDEN` for any reference that is not their workspace (existing or not, so no oracle); admin gets `E_NOT_FOUND`; there is no "default" or "first" workspace; `workspace` must always be given | `Authorisation.test_unknown_workspace_*`, real `test_incorrect_workspace_ids_fail_closed_without_a_fallback` |
| An agent takes more power than it was given | agent credentials cannot create/destroy/assign/enter workspaces, `resume` a takeover, resolve approvals, change the clipboard policy, issue credentials, decide grants; unlisted methods are denied; an agent cannot claim `agent_kind: human` to bypass takeover | `Authorisation.test_agents_cannot_use_human_or_admin_methods`, real `TakeoverAndRelease` |
| An agent overwrites your files through the API | `screen.screenshot path` is confined to `<workspace>/shots/` for agent credentials | `Authorisation.test_screenshot_path_is_confined_for_agents` |
| Agent input or screenshots reach the personal desktop | `WorkspaceSession` takes an explicit socket path and never reads the environment; before every call the routing identity check below; no `xdotool`/`ydotool`/`uinput`/`wtype`/`grim` anywhere in the code (static audit) | `NoHostDisplayInTheCode`, real `RoutingFailures` (daemon started with its environment pointing at a stand-in personal desktop; nothing reached it) |
| Apps of a workspace read your files or reach the daemon | opt-in `--sandbox` (below) | real `test_sandbox_real.py` |

## Credentials

* **Format and storage.** `awt1_<workspace id>_<256 random bits>`. The daemon keeps only SHA-256 hashes (`<workspace>/credentials.json`, 0600). The token exists in the 0600 file `<workspace>/token` (and `<base>/admin.token`), and in the process that was handed it. Tokens are never in argv, logs, the audit log, error messages or event streams. Files that are not owned by you with mode 0600 are regenerated by the daemon and refused by the client. (`Credentials.*`, `AuditAndLogs.*`)
* **Kinds.** Default workspace credential (scopes `read screenshot input launch windows clipboard approval`); issued credentials (`credential.issue`, chosen scopes, 1 s to 24 h); exchanged credentials (`auth.exchange`: a short-lived subset of the caller's own scopes, never `admin`, never outliving its parent: what an MCP session or a sub-agent should be given); the admin credential for the human (CLI, viewer, panel extension).
* **Rotation and revocation** take effect immediately, also on connections that are already open (`UnauthorisedAndWrongIds.test_revocation_and_rotation_hit_connections_that_are_already_open`). Event streams re-check the credential at each event and end with an `auth.revoked` event (implemented, not covered by a test). Rotating the admin credential ends existing admin sessions.
* **Brute force.** Failed authentication is slowed down and the connection is closed after 10 failures (`test_throttle_and_close_after_repeated_failures`). Tokens are 256 bits.
* **Lookup order** used by the Python client (so callers never hand-roll sockets or tokens) is in [api.md](api.md#credential-lookup-order-python-client-awclientclient-used-by-the-cli-the-mcp-server-and-the-viewer). A client that was configured with an agent token never falls back to the admin credential.

## Explicit human authorisation (grants)

Sensitive operations need a grant that only a person can give. Implemented as generic plumbing (`aw/grants.py`, `grant.*` in [api.md](api.md)); the kinds today are `browser_profile` (use a copy of a signed-in browser profile; the resource is the profile name) and `host_clipboard`.

* **Agents can only request** (`grant.request`, scope `approval`) and check (`grant.check`). `grant.resolve` and `grant.revoke` need the admin credential **and** a human channel; with an agent credential, or through MCP, they are unreachable (`E_FORBIDDEN`).
* **Human channel**, decided by the daemon from the connecting process (`SO_PEERCRED` pid): an interactive terminal (the process has a controlling terminal and its stdin is a tty), the shipped viewer, or GNOME Shell. Otherwise `E_NOT_HUMAN_CHANNEL`. The CLI (`agent-workspaces grants approve|deny|revoke ID`) refuses to run without a terminal and asks you to type a confirmation word. Verified with the real CLI on a real pseudo-terminal, and refused without one (`HumanGrants`).
* **A grant** is bound to workspace, kind and resource, lasts 15 minutes by default (maximum 8 hours), can be revoked, and dies with the workspace. Persisted in `<base>/grants.json` (0600, metadata only).
* **Using it.** Code that performs the sensitive operation must call `Daemon.grants.require(workspace_id, kind, resource)` first. It raises `E_GRANT_REQUIRED` and logs the refused attempt when there is no live grant. SA-side features (profile cloning, clipboard bridge) must call it; this branch provides the plumbing and tests, not those features. The clipboard policy itself (`workspace.configure clipboard=...`) can no longer be changed with an agent credential.
* **Logging.** `grant.requested|granted|denied|revoked|used|refused_use|refused_channel` with workspace, kind, resource label, channel and expiry. The free-text `detail` of a request and any secret contents are not copied to the log.
* **Honest limit.** A hostile process running as you can read `admin.token` and allocate a pseudo-terminal, so the channel check is a speed bump against it, not a barrier. It is a real barrier against everything that only holds an agent credential, which is how agents are meant to be configured.

## Routing guarantees (screenshots and input)

Before **every** call that talks to a workspace compositor, `Manager.verify_routing` checks that: the workspace is running; the socket path is exactly `<base>/<id>/rt/wayland-0` and its directory resolves inside the base directory; the path is a socket (not a symlink or file) owned by you; the recorded compositor pid is alive, not a zombie, and has the recorded start time (a reused pid counts as dead). When a connection is made, the pid behind the socket (`SO_PEERCRED`) must equal the recorded compositor pid, **checked before the first Wayland byte is sent**. A cached connection is dropped when the socket inode changes. If a call fails because the connection broke, routing is re-verified and the error is `E_NOT_RUNNING` (compositor gone; the workspace is recorded as stopped) or `E_ROUTING` (something else serves the socket). No branch of the code falls back to another socket or to the environment.

Tests with real compositors: killed compositor (all routes answer `E_NOT_RUNNING`), stale socket file, a different process listening at the workspace's socket path (`E_ROUTING`, and the imposter received zero bytes), a symlink to someone else's socket, a daemon whose environment points at a stand-in personal desktop (that desktop's probe window, pointer and window list were unchanged after dozens of failing operations).

## Sandbox for the apps of a workspace (opt-in)

`agent-workspaces create --sandbox [--sandbox-mount PATH[:rw]] [--sandbox-no-network]` runs every app launched into that workspace under bubblewrap. See [isolation-model.md](isolation-model.md#optional-sandbox-for-workspace-apps) for exactly what is visible, measured overhead and compatibility. Summary: private `HOME`, read-only system, private `/tmp`, own PID/IPC/UTS namespaces, none of your files, the API socket, token files, other workspaces or the host display/bus/PipeWire sockets, unless you mount a project directory. **Not** provided: no seccomp filter; the network namespace is shared by default (so abstract unix sockets of the host, including the host X server's, are reachable; `--sandbox-no-network` closes that); the compositor and the workspace's session bus are outside the sandbox and trusted; Chrome runs inside it only with its own sandbox disabled. It is a layer that was tested against the specific checks in `test_sandbox_real.py`, not a hardened boundary against kernel or driver exploits.

## Audit log

`<base>/audit.log` (0600, rotated at 4 MiB): who (credential id and kind, peer pid), what (method name), which workspace, outcome. It records denials, authentication failures, workspace/credential/approval/grant changes, launches and viewer attaches; **not** parameters, typed text, clipboard contents, screenshots, tokens or the free text of requests. Read with `agent-workspaces audit` (admin).

## Not provided (do not rely on it)

* **A hostile process running as you can do everything the human can**: it can read `admin.token` and every `token` file, connect to every workspace compositor socket, ptrace your processes. Credentials separate agents that were given a scoped token; they do not confine malware. Run agents in containers/VMs or under another account if you need that.
* **The workspace compositor socket is reachable by any process of your user** (and by any app in a workspace: the daemon itself drives the compositor as an ordinary Wayland client through its virtual-input protocols, so another client of that socket can too; not separately tested from inside an app). A program that connects to it directly bypasses the daemon's takeover (`E_PAUSED`) and scope checks. Apps inside a `--sandbox` workspace can reach only their own workspace's compositor.
* **Without `--sandbox` apps run as you** with your files and network. An agent that can run commands can use `xdotool`-style tools against your real session; the integration instructions tell it not to, nothing enforces it. Only `--sandbox` removes the files and sockets from view, and even then not the network unless asked.
* **Screenshots may contain secrets** shown in the workspace; they are returned to the calling agent.
* **Browser profiles**: nothing here copies or protects a signed-in profile. A browser in a workspace gets the workspace's private `HOME` (empty profile) by default. Two workspaces may not use the same `--user-data-dir`/`-profile` directory at the same time (`E_PROFILE_BUSY`), because Chromium hands a second launch to the instance that owns the directory (measured with Chrome: the page of one workspace opened inside the other workspace's browser). Two workspaces with `--home shared` that start the same browser without an explicit profile directory are not detected.
* **The GNOME extension** runs inside GNOME Shell with Shell privileges and now reads `admin.token`; read its source before enabling it.
* **Audit log and grants are plain files of your user**: a process running as you can edit them.
