# Limitations (what is not done or not claimed)

* **Not a security boundary against a hostile same-user program.** See [security-model.md](security-model.md). The API is authenticated with per-workspace scoped credentials, but a process running as you can read them; the workspace compositor socket is reachable by same-user processes; filesystem/process confinement exists only with `--sandbox` (no seccomp, shared network by default, Chrome needs `--no-sandbox` inside it).
* **Ubuntu GNOME on Wayland only**, developed on Ubuntu 26.04 / GNOME Shell 50.1. Other distributions and desktops are untested.
* **labwc 0.9.3 specifics**: it announces some X11 windows through wlr-foreign-toplevel (`xmessage`, Chrome on X11) and not others (`xeyes`, `xclock`), so `window.list` also reads the workspace's own X server ([windows.md](windows.md)). Wayland window geometry cannot be read: it is `unknown` until a window is placed or maximized. Moving/resizing a Wayland window rewrites the workspace `rc.xml` and reconfigures labwc (0.3 to 0.7 s, focuses the window). A client-side-decorated Wayland window is placed with a (1, 27) px decoration offset.
* **Typing** uses the `us` keymap. Characters not in that layout are pasted through the workspace's own clipboard (needs the focused app to support Ctrl+V); not tested with non-Latin text in real apps.
* **Audio** is output only: a private PipeWire null sink per workspace that you can record; no microphone or capture source; routing to the host speakers is off by default, human-only, and was tested only against a stand-in PipeWire, not your real speakers ([audio.md](audio.md)).
* **Browsers**: snap and flatpak browsers are refused (the Ubuntu `firefox` here is a snap); only Google Chrome 152 (deb) and a Firefox 160 vendor tarball were tested; Brave, Edge, Vivaldi, Chromium and the Firefox deb were not available. Signed-in user profiles are available only as a human-authorised, allow-listed copy; Chromium cookies encrypted with your desktop keyring cannot be read in the copy; no real profile of yours was ever read or copied in testing ([browsers.md](browsers.md)).
* **Agent integrations**: model-driven computer use inside the agent's own workspace was verified for Claude Code (Haiku 5.5), OpenAI Codex (GPT-6-Luna), Antigravity (Gemini 3.8 Flash low) and Hermes (Qwen3.6-35B-A3B on the Spark router), on small tasks, through per-invocation configuration only. Antigravity's flash model failed the two-app task; it needs the rule text in `~/.gemini/GEMINI.md`, and its login is read from the desktop keyring through a filtering D-Bus proxy. Hermes needs the model declared vision-capable. `integrate <agent> install` on the real configurations, and the skills it writes, were not exercised in a live agent. See [compatibility-matrix.md](compatibility-matrix.md).
* **The viewer** forwards pointer, buttons, scroll and keys. Not implemented: touch, pointer lock, high-resolution scroll, IME composition, drag and drop between your desktop and the workspace, file transfer. Clipboard bridging is plain text only and the host-clipboard side of the viewer was not tested automatically. The viewer copies each frame through shared memory in Python: about 38 % of one core in a software-rendered stand-in desktop under continuous motion (see measurements). It has not been run on a real GNOME session by me.
* **The GNOME extension** was tested only in an isolated headless GNOME Shell 50 with a private session bus and private stand-in system bus: not on the live session, not with multiple monitors, ubuntu-dock or blur-my-shell. It uses private Shell API and is GNOME 50 only. See [gnome-extension.md](gnome-extension.md).
* **Electron**: tested with the stock Electron binary from npm (a minimal test app), not with any other application. **Chromium**: tested with Google Chrome with `--ozone-platform=wayland`. **GTK4**: tested. **XWayland**: tested with xeyes. GTK3, Qt and Firefox: not tested.
* **Application compatibility** is in [compatibility.md](compatibility.md): GTK3 and GTK4 (also libadwaita), Qt6 (native Wayland), Qt5 (via XWayland, no Qt5 Wayland plugin installed), Electron 33 (stock, needs `--no-sandbox`), Chrome, Firefox and X11 clients were run for real. Not run: Qt5 on native Wayland, a deb Firefox, Chromium proper, SDL/Java/Wine apps, anything that needs a desktop portal (`GTK_USE_PORTAL=0` is set; there is no portal in a workspace).
* **GPU**: verified on NVIDIA (driver 595.99.02) only. Intel/AMD paths, multi-GPU selection (`--render-node` exists but is not exercised) and GPU memory limits are untested.
* **Manual takeover** blocks agents that go through the daemon/MCP/CLI. It cannot stop a process that talks to the workspace socket directly.
* **Daemon restarts** keep workspaces running and re-adopt them (metadata is under `$XDG_RUNTIME_DIR`, so they do not survive logout or reboot). Tested with a SIGKILLed daemon and real compositors and apps. A crashed compositor is not restarted automatically: `workspace.start` recovers it.
* **Gnotch**: the API (docs/api.md) was written to the stated needs; I did not run Gnotch against it.
* **The second (remote) test machine** was unreachable when I tried to run the unit tests there (SSH connection timeout); all test runs were on the workstation.
